## CRT 중앙 배정 운영

연구자 작업실에서 설계·인원·파일럿/본 실험을 선택한 뒤 중앙 배정표를 생성합니다. 원자적 트랜잭션으로 `state/counter`를 하나 올리고 익명 UID의 `claims`를 고정합니다. 재시도는 같은 배정을 반환합니다. 동시 변경으로 오래된 트랜잭션이 거부되면 전체 트랜잭션을 제한된 횟수만큼 다시 실행합니다. 서버 규칙을 우회하지 않습니다.

관리자는 배정표를 볼 수 있으므로 참가자 진행 담당자와 분리합니다. 참가자는 미래 슬롯·목록을 조회할 수 없지만, 현재/과거 익명 슬롯의 단건 읽기는 가능합니다. 강한 서버 함수 배정 비밀성과 계정 단위 중복 참여 차단을 제공하는 구조는 아닙니다.

공용 기기는 완료·서버 수신 확인 뒤 ‘새 참여 준비’로 익명 계정을 교체합니다. 진행 중 브라우저 데이터를 지우거나 시크릿 창을 닫으면 재개·소유권 연결을 잃을 수 있습니다. 네트워크 실패 중에는 현재 기록을 JSON으로 보관하고 기존 브라우저에서 재전송합니다.

규칙 배포: `firebase deploy --only firestore:rules --project hci-judgment-20261107`. Pages 코드 배포와 별개입니다. 이번 로컬 작업에서 실제 규칙 배포·새 배정표 생성·실제 응답 업로드는 실행하지 않았습니다.

# Firebase 자동 수집 운영

프로젝트 `hci-judgment-20261107`, Firestore Standard `(default)`, 서울 `asia-northeast3`. 결제 계정 연결 없이 무료 할당을 우선한다. 무료 할당 소진 시 전송 실패가 발생할 수 있으므로 실제 사용량은 Firebase 콘솔에서 확인한다. GitHub Pages는 화면을 배포하고 Firebase는 응답·행동 기록을 보관한다.

참가자는 동의 후 익명 인증으로 자기 실행의 응답과 행동을 전송한다. 연구자 작업실에서는 `superriaco@gmail.com`, `tigers0214@gmail.com`, `slightsmille@gmail.com`의 이메일 확인된 Google 로그인에만 서버 조회를 허용한다. 참가자·연구자의 인증 저장 공간은 분리한다. 웹 앱 설정은 공개 식별자이며 관리자 자격증명이나 로그인 토큰을 저장소에 넣지 않는다.

## 참가자 흐름

실제 Pages 주소에서 자동 수집이 활성화된다. 로컬 개발은 `http://127.0.0.1:4173/hci/?cloud=1`에서 명시적으로 활성화한다. 기본 로컬·DOM 시험은 클라우드에 보내지 않는다. 시작 전 안내는 자동 전송·서울 서버 보관을 알리고, 이전 로컬 실행은 추가 동의 뒤에만 전송한다.

브라우저에 원본을 저장하면서 약 15초 간격으로 변경된 응답·행동을 전송한다. 네트워크 실패는 로컬 기록을 삭제하지 않고 다음 시도에 재전송한다. 기록 파일 다운로드도 복구 경로로 유지한다. 브라우저 데이터를 지우거나 탭을 강제 종료하면 아직 전송되지 않은 마지막 기록이 유실될 수 있다.

‘응답 작성 완료’와 ‘최종 응답 서버 수신 확인’은 다르다. 완료 후 서버 수신 확인 버튼으로 재시도할 수 있다. 수신 확인은 최종 응답과 해당 시점의 이벤트 묶음 목록·개수·식별자 해시를 서버에서 다시 읽어 확인했다는 뜻이며, 응답의 진실성·정답성이나 이후 모든 브라우저 이벤트의 영구 보관을 보증하지 않는다.

## 연구자 작업

1. [연구자 작업실](https://minestero00.github.io/hci/research.html)에서 지정 Google 계정으로 로그인한다.
2. 서버 자료 가져오기를 누른다. 최종 수신 확인과 로그 목록이 일치한 완료 실행을 가져온다. 미완료·불일치 실행은 경고로 보고한다.
3. 팀 자유 체험은 기존 `demo`로 구분되며 기본 분석 CSV에서 제외한다. 본 파일럿에는 생성한 참여 링크를 제공한다.
4. 기존 블라인드 채점·합의·CSV·전체 보관 JSON 절차를 사용한다. 서버 조회가 채점 결과를 자동으로 서버에 올리는 기능은 아니다. 채점·초대·보관 자료는 연구자 브라우저와 내보낸 파일에 보관한다.

동일 실행의 다른 응답·로그는 기존 가져오기 정책처럼 충돌로 유지한다. 중간 JSON을 먼저 가져왔다면 완료 서버 자료와 충돌할 수 있으므로 정상 수집에서는 최종 서버 확인 자료를 기준으로 사용한다.

## 데이터와 접근 규칙

- `runs/{runId}`: 소유 익명 UID, 응답 JSON, 갱신 시각.
- `runs/{runId}/chunks/{chunkId}`: 최대 100개·약 180KB의 이벤트 묶음. 식별자 SHA-256으로 재시도 중복을 줄인다.
- `runs/{runId}/receipts/final`: 완료 응답의 이벤트 목록·개수·해시·제출 수·완료 시각·UI 버전 수신 확인.

Rules는 자기 실행만 쓰고 읽도록 하며 타인의 조회·목록·수정·클라이언트 삭제는 막는다. 연구자만 전체 조회할 수 있다. 이벤트 묶음은 동일 내용 재전송만 허용한다. 큰 JSON은 인덱싱하지 않는다.

클라이언트가 보낸 JSON 본문은 서버 Rules가 과제별 논리까지 검증하지 않는다. 소유 참가자의 조작·가짜 참여를 완전히 차단하거나 서버에서 무작위 배정·채점을 수행하는 구조가 아니다. App Check와 강한 초대 검증은 아직 적용하지 않았다. 안내된 소규모 실제 테스트를 위한 수집이며 공개 대규모 모집 전에는 남용 방어·사용량과 운영 절차를 추가 점검한다.

정답과 문항·루브릭은 기존 공개 저장소에 이미 공개된 이력이 있다. DB 연결이 이를 비공개로 되돌리지 않는다. 정답 비밀성이 필요한 본 실험은 새 비공개 문항·키를 별도로 관리해야 한다.

담당자 연락 방법·보관 종료일은 실제 모집 전에 확정해야 한다. 프로젝트 생성과 수집 연결 자체가 모집 안내의 모든 운영 결정을 대신하지 않는다.

## 검증과 배포

로컬 전체 시험은 54개 통과·라이브 전용 2개 기본 건너뜀이다. 별도로 실제 Firebase에서 라이브 권한·최종 수신 왕복 시험 2개를 실행해 모두 통과했다. 합성 응답과 임시 인증 계정은 해당 시험에서 정리했다. Google 연구자 팝업 로그인은 실제 계정의 브라우저 확인이 남아 있다.

`npm run check`는 클라우드 수신·실패 재시도와 수신 확인 검증, 기존 참가자·연구자 흐름을 시험하고 Firebase 브라우저 SDK를 로컬 묶음으로 빌드한다. Firebase SDK가 외부 서버로 요청하는 실제 연결은 별도 라이브 시험으로 검증한다.

`HCI_FIREBASE_LIVE_TEST=1 node --test tests/firestore-rules.test.mjs`는 전용 프로젝트에 임시 익명 계정·합성 응답을 만들고 권한·최종 수신 왕복을 확인한 뒤 자신이 만든 자료만 정리한다. 기본 CI에서는 이 시험을 건너뛴다. 실제 연구자의 Google 팝업 로그인과 브라우저의 시각·네트워크 체감은 실제 계정으로 확인해야 한다.

규칙·인덱스·인증 설정 배포는 로그인된 로컬 CLI에서 `firebase deploy --only auth,firestore --project hci-judgment-20261107`로 수행한다. GitHub Actions에는 관리자 키를 넣지 않으며 웹 배포만 담당한다. 유료 요금제 전환·Cloud Functions·자동 유료 백업은 이 구현에서 사용하지 않는다.
