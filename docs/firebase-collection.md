허용 연구자 이메일은 `superriaco@gmail.com`, `tigers0214@gmail.com`, `slightsmille@gmail.com`입니다. [클라이언트 확인](../web/crt/cloud.mjs)과 [Firestore 규칙](../firestore.rules)이 이를 검사합니다. 참가자 인증 앱과 연구자 인증 앱은 분리되어 있습니다.

운영 화면의 Google 로그인은 연구자가 직접 완료해야 합니다. 관리자 CLI의 IAM 권한으로 수행한 합성 자료 가져오기 검증을 브라우저 Google 인증·규칙 검증으로 대신하지 않습니다.

배포 도메인은 `minestero00.github.io`, Firebase 기본 도메인, `localhost`가 승인되어 있습니다. 로컬 참가자의 자동 서버 수집은 기본값에서 꺼져 있으며 `?cloud=1`을 붙이면 켜집니다. **연구자 화면의 Google 로그인·서버 자료 가져오기·서버 중앙 배정표 생성 버튼은 이 옵션 없이도 설정된 실제 Firebase에 연결을 시도합니다.** 실제 서버를 쓰지 않을 때는 로컬·오프라인 초대와 파일 가져오기를 사용하고 서버 버튼을 누르지 마세요. Google 로컬 로그인에는 승인된 `localhost`를 사용해야 하며 `127.0.0.1`과 같은 도메인으로 간주하지 마세요. 실제 연구자 인증 확인은 우선 배포된 작업실에서 수행하세요.

## 중앙 배정과 참가자 진행

1. 연구자는 작업실에서 준비 인원·집단 간/집단 내 설계·사람 파일럿/본 실험을 선택합니다.
2. 중앙 배정표의 슬롯·카운터를 준비한 뒤 모집을 엽니다. 기본 설계는 두 집단 × 세 라틴 순서의 6조합 블록입니다.
3. 동의한 참가자가 최초 온라인 접속하면 트랜잭션으로 순번을 올리고 익명 UID별 claim을 고정합니다. 같은 UID의 재시도는 같은 배정을 반환합니다.
4. 참가자는 같은 브라우저에서 중단·재개합니다. 이탈한 순번을 재활용하지 않습니다.
5. 공용 기기는 완료와 서버 수신 확인 뒤 ‘새 참여 준비’를 눌러 익명 계정을 교체합니다. 수동 초대의 경우 다음 참가자의 새 링크를 열어야 합니다.

로컬·오프라인 초대는 순번을 담당자가 전달하는 대체 경로입니다. 중앙 배정과 수동 초대는 CSV의 `allocation_source`로 구분합니다. 첫 참가자 이후 설계를 바꾸거나 두 설계의 자료를 합치지 않습니다.

참가자는 슬롯 목록을 읽지 못하지만, 규칙상 현재 카운터가 가리키는 슬롯과 그 이전 슬롯의 단건 읽기는 가능합니다. 연구자는 배정표 전체를 볼 수 있으므로 **배정표 관리자와 참가자 진행 담당자를 분리**해야 합니다. 중앙 배정을 강한 기술적 배정 은폐나 사람 단위 중복 참여 차단으로 설명하지 마세요.

## 저장·수신 확인·가져오기

| 위치 | 저장 내용 |
|---|---|
| `crtBatches/{batchId}` 및 하위 `slots/state/claims` | 설계·수집 종류, 준비된 배정, 카운터와 UID별 claim |
| `runs/{runId}` | 소유 UID, 응답 JSON, 갱신 시각 |
| `runs/{runId}/chunks/{chunkId}` | 최대 100개·약 180KB로 묶은 이벤트. 묶음 ID는 이벤트 식별자 해시 |
| `runs/{runId}/receipts/final` | 최종 제출 수·완료 시각·이벤트 목록/개수/해시·UI 버전 수신 확인 |
| 참가자 브라우저 | 초안·응답·행동 기록의 로컬 사본 |
| 연구자 브라우저 | 가져온 사본, 채점 묶음·독립 점수·합의·변경 이력·초대 보관 |

참가자 동의 뒤 단계별로 전송할 응답 사본을 갱신하고, 약 15초 간격과 최종 제출 시 서버로 전송합니다. ‘응답 작성 완료’와 ‘최종 응답 서버 수신 확인’은 다릅니다. 최종 확인은 서버에서 응답과 chunk 목록·이벤트 범위를 다시 읽어 일치함을 확인했다는 뜻입니다. 이후 생긴 모든 이벤트의 영구 보관이나 응답의 진실성을 보장하지 않습니다.

연구자의 ‘서버 자료 가져오기’는 v4 형식이 유효한 미완료 실행도 명부에 보존합니다. 완료 실행은 receipt와 chunk를 검증합니다. 형식·소유권·수신 확인이 맞지 않는 자료는 경고로 보고하므로 별도로 조사해야 합니다.

같은 실행을 다시 가져올 때 고정 메타데이터·기존 제출 이력이 같고 기존 이벤트를 모두 포함하는 **진행된 후속 스냅샷**만 갱신합니다. 분기 이력·동일 단계의 다른 자료는 충돌로 남습니다. 전체 보관 JSON은 수집 자료와 채점을 함께 보관하는 백업이며, 채점이 자동으로 Firebase에 올라갔다고 생각하지 마세요.

## 배포

Pages와 Firebase는 별개입니다. main에 머지하면 [GitHub Actions](../.github/workflows/pages.yml)가 시험·정적 빌드 후 Pages를 자동 배포하지만 Firebase 설정은 바꾸지 않습니다.

```sh
# 사용할 CLI 계정과 프로젝트 권한을 먼저 확인
firebase login:list

# 저장소 설정대로 인증·Firestore 규칙·인덱스 배포
firebase deploy --only auth,firestore \
  --project hci-judgment-20261107 \
  --account superriaco@gmail.com \
  --non-interactive
```

규칙만 변경했다면 `--only firestore:rules`로 범위를 줄입니다. 배포 후에는 Pages 성공 상태, 실제 정적 파일, 적용된 Firebase 설정과 필요한 범위의 라이브 시험을 구분해 확인합니다. UI·문서만 바뀌었으면 Firebase를 다시 배포할 필요가 없습니다.

이 저장소는 관리자 키를 GitHub Actions에 넣거나 유료 요금제 전환·Cloud Functions·자동 유료 백업을 구성하지 않습니다. 실제 사용량·할당·결제 상태는 [Firebase Console](https://console.firebase.google.com/project/hci-judgment-20261107/overview)에서 확인하세요.

## 운영 전에 남는 제약

- 연구자 Google 직접 로그인 후 서버 조회·배정표 게시의 사람 확인, 사람 파일럿·모집/보관 정책 확정은 [남은 확인 항목](crt-v4.md#사람이-확인할-항목)을 따릅니다.
- 브라우저를 바꾸는 동일인의 재참여, 소유 참가자의 조작·가짜 응답을 완전히 차단하지 못합니다. Rules는 JSON 본문의 연구 논리까지 검증하지 않습니다.
- App Check·강한 초대 검증·서버 함수 기반 배정 은폐는 적용하지 않았습니다. 공개 대규모 모집에는 남용 방어·사용량과 운영 절차 검토가 필요합니다.
- 정답·루브릭은 공개 저장소에 이미 존재합니다. Firebase 연결이 정답 비밀성을 만들어 주지는 않습니다.
